# Repository instructions

Read and follow the full applicable global, parent-directory and repository instruction chain before acting. Delegated agents must do the same before starting work.

- The authoritative plan is `docs/COLLABORATIVE_LATEX_PLAN.md`; release definitions and gates are in section 9. Section 0 of the plan (working-product order, 14–15 November 2026) sets the order of work and overrides older ordering here and in the plan: working states WS1–WS5, build first and check after. Application implementation is authorized in that order; do not hold planning-only or tooling-only sessions unless the user asks. Starting a container or server for the first time, exposing a port, using real accounts or projects, and modifying or copying upstream source still need the user's explicit go-ahead.
- R0–R7 are eight incremental releases. Finish the current phase's scoped implementation and actual checks before advancing; do not wait for later features to release an earlier usable increment. Do not ask for routine successful phase transitions.
- Get the current working state running first, then run its feasibility checks and gates once on the running instance, then fix what they found. A conclusive unsupported result documents a limitation, not a passing live-feature test. Stop dependent feature work when its premise fails.
- Keep schema-3 `docs/phase-status.json` accurate. Candidate/production target `releasePhase` and require passed prerequisites through that phase, not the whole roadmap. Never pass mocked-only, skipped, unavailable or unexecuted required checks. Reopen invalidated phases and reset dependents.
- Product: a browser-based web UI, not a VS Code extension. Retain nearly all selected upstream capabilities and add recovery/session safeguards and required multi-user server job distribution. Do not silently exclude features or count extension-only workflows as web equivalents. Preserve Windows/macOS browser behavior, review metadata, candidates and server identities. No Premium dependency. Discover the smallest upstream-compatible web integration; resolve licensing before source incorporation. Use synthetic projects for mutation tests.
- Add only tests for actual capabilities, relevant failure boundaries and affected regressions. No fixed test counts, blanket performance/security certifications, mandatory multi-day pilots or dual-engine benchmarks. The plan gate table is authoritative. Do not remove regressions guarding actual defects.
- Reuse the CE+ browser/editor/engine and existing queues/workers first. Use Rust for missing custom backend functions; retain reused JS/TypeScript in its required host language. Shared server job distribution is required R7 scope with early R0 feasibility probes, not optional scaling. Browser/local-file/local-compile support requires discovery; no unproven extension API or local helper assumption.
- Planning assets contain no working web application. R0 adds actual web/service packaging and real supported-browser smoke checks before distribution; no VSIX/Marketplace pipeline and no passing placeholder application checks. Historical extension experiments are not browser qualification.
- Maintain the inventory of dependencies actually introduced.
- Before edits, inspect affected context and define scoped changes and validation. Do not modify adjacent projects.
- Run `npm ci`, `npm run typecheck`, `npm test`, `npm run validate`, `npm run build`, and `npm run test:package` for repository/release changes. Build/package requires a commit containing the intended inputs; an isolated temporary Git snapshot is acceptable for local verification without committing the working checkout. Application phases add their actual tests.
- Keep publication gated on CI and verify downloaded assets/source/checksums. The legacy planning publisher is disabled; main pushes run checks and produce source snapshots only. Versioned application releases require explicit authorization and verified installable assets. Source pushes do not authorize deployment, license changes or external integration activation.
- Keep design, assumptions, release gates and implementation status in the plan; do not create a separate STATUS.md. Evidence reports support the plan rather than duplicating it.
