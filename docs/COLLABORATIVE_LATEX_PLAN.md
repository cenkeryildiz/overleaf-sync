### Server-first delivery, later browser computation and account access — user direction, 16 November 2026

**First-version decision (16 November 2026; takes precedence over earlier browser-computation proposals).** Keep computation on the application server: the host contains TeX, packages/fonts and the PDF/preview services, and performs compilation for participants. Participants open the web UI and need no TeX distribution, compiler setup, Docker or development-source checkout on their PCs. The current Mac-hosted CE+ installation remains the implementation baseline. Preserve responsive editing/carets, accurate final PDF/source navigation and fair concurrent compilation; simple text editing does not imply all LaTeX documents are cheap to compile. Measure representative diagrams, figures, bibliography/cross-reference passes and simultaneous users before making capacity or latency claims. Optimize the existing path first. Browser computation, a distributed pool of participant PCs and VS Code are not prerequisites for this first version.

**Hosting remains deliberately undecided.** The user will decide later how another machine or provider can host the application so their Mac does not have to remain open, awake or running. Do not assume a paid host, free cloud VM, static hosting, rotating participant hosts or any specific migration has been selected. The present Mac must remain powered/awake, running and reachable to serve others; if it is unavailable, server-dependent editing/saving/compilation cannot be promised. GitHub can store/synchronize project files and history, but ordinary repository/static-site hosting does not run this compilation server. Record the future hosting decision separately with measured resource needs, permissions/security, reliable private storage, backups/recovery and zero-charge constraints. No public deployment or provider activation is authorized here.

**Later comparison objective (deferred).** Preserve HOST-01/HOST-02 and the free storage/local-computation research below as future options, not the first-version shipping architecture. The browser alternative would use each participant's computer without a conventional TeX installation and could prepare selected projects for offline compilation. It remains unimplemented/unqualified and is not required before delivering the server-compute version. The user remains concerned about public-server exposure; GitHub storage does not eliminate application security responsibilities. Preserve the working CE+ baseline and VITAL speed/navigation priorities. Implementation remains paused; this request updates the plan only.

**Current verified state and boundaries.** The working installation runs CE+ services, MongoDB, Redis and native TeX on the Mac; its browser is not yet a standalone offline TeX runtime. Native/TeXpresso measurements do not establish WebAssembly speed or fidelity. Browser TeX candidates already identified in this plan (SwiftLaTeX and TeXlyre-BusyTeX) demonstrate a plausible reuse path, but the representative document, packages, bibliography, graphics, fonts, SyncTeX and licensing must work together before adoption. Static hosting alone cannot run the existing CE+ backend. **Efficiency requirement.** Compare existing helpers, platform facilities and maintained packages proportionally to this workload; minimize installed/downloaded size, dependency graph, startup, allocations, memory and I/O while preserving correctness, security and maintainability. Prefer on-demand required resources and measured whole-workflow gains; a smaller bundle, Rust implementation or cache is not by itself proof of improvement.

**Later browser-computation operation (deferred; not first-version behavior).** Open the website; load the editor and browser-compatible compiler; fetch only necessary package/font resources; compile on the user's device; use online services for authorized private storage and collaboration. “No TeX installation” does not mean zero download, zero RAM or zero local disk use: executing locally requires code/resources to reach browser memory, and offline use requires retained local copies. Use measured initial/warm download size, cache size, peak memory and actual rendered-preview latency, not nominal engine speed. Request persistent browser storage where supported, handle denied permissions/quota/eviction visibly, and provide exact-source export. A first-ever offline visit or compilation needing an uncached package cannot be promised to work. Do not expose private project content or source-derived resource names to an arbitrary public package-fetch service.
