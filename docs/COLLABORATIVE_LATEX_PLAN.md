## Stage 1 behavior

**Write LaTeX and see an updated PDF.** Stage1 is a useful offline LaTeX editor, not only a text editor or an existing-PDF reader. Create/import a project, edit source, automatically compile accepted changes locally and view the newly generated real PDF. Provide manual recompile, stop/cancel, bounded diagnostics and faithful forward/inverse source navigation tied to that output's exact revision. Preserve saved autocompile Off preferences; for new projects provide autocompile by default. Coalesce/debounce edits, bound outstanding work and never publish a result for superseded source. Keep the last valid PDF on errors, visibly mark it stale when appropriate and preserve exact unsaved source.

**Runtime boundary.** No separate system TeX distribution, account, server or internet connection is required for stage1 use. Reuse the existing browser/local compiler integration and pinned resources before introducing another engine; no new compiler survey is requested. Package or explicitly prepare and retain the needed public engine/packages/fonts before claiming a project is ready offline. Browser execution still requires local resources and storage: uncached/missing packages must fail visibly without losing source/previous output, not download silently during offline use. Do not advertise unsupported packages or a first-ever disconnected startup that lacks its resources. Record actual compiler bundle/cache footprint and initial/warm latency, rather than promise a small download or instant compilation. Stage3 remains optional installed-TeX contributor distribution and research tools, not the first availability of compilation.

**Files, recovery and existing PDFs.** Keep stage1 create/import/edit/save, file/folder create/upload/rename/move/main/delete/restore, preferences, exact export/reopen and conflict/interruption safeguards. Opening an existing PDF remains supported, but identify it as supplied output: source edits update the generated compiler output only after a successful local compile, and a supplied PDF alone establishes no source mapping. Reject invalid supplied/generated outputs while preserving the last valid PDF and original data.

## Stage 2 behavior — LAN collaboration

**Prerequisite:** published/accepted stage1 offline editing. LAN sharing and participant permissions are a separate release; they must not block the first offline publish.

**Share on this network.** The owner clicks a button in the editor. Show a join link and a separate generated passcode. A participant opens the link, enters the passcode and chooses a username for this session. No account, existing LaTeX server, internet connection or TeX installation is required. The link may contain routing/public host identity, never a passcode or bearer token. Keep codes/tokens outside logs, URLs and persistent storage; validate usernames and render them as text. Show participants/carets using their session names. Stop sharing revokes access; a new room uses a new passcode. No public reachability, port forwarding or automatic listener startup.

**Owner-controlled capabilities.** The owner can set each participant to:

- **Edit while host is online** (default): edit only during the authenticated session. Host loss/disconnect locks editing until authenticated rejoin. No project persistence, recovery download, export, offline continuation or transfer into another mode. Keep pending unacknowledged edits in session memory for explicit reconciliation. Restricted source data must not enter IndexedDB, localStorage, native editor backups, service-worker caches or logs.
- **Keep a copy and continue elsewhere**: explicitly save an independent local copy, export and continue offline or in another available mode. Returning changes requires explicit comparison/merge; never overwrite the shared project automatically. Future modes remain unavailable until their stage ships.

In restricted sessions, inherited local PDF compilation must keep private source/intermediates/generated output in session memory and respect disabled export/persistence; public compiler resources may be cached separately. Do not silently persist a restricted project to make compilation work.

Only the owner grants/changes these permissions. Enforce them at host request authorization and every participant save/export/download/transfer path; hidden buttons are insufficient. Downgrades stop future copying but cannot recall previously retained copies. These are application permissions: participants who can read source can manually copy it outside the app. Owner originals and authorized independent copies remain recoverable.

Reuse `runtime/chrome-extension/native/src/tex.rs` confinement/cancellation and the existing `runtime/participant-compile/` job lifecycle where compatible; do not replace either with another queue or engine without a demonstrated gap. The owner's coordination role does not make the host a required TeX worker. Selection means an explicit participant choice of a local installation, with packages supplied separately; do not download/install TeX silently.

Prepare immutable source/assets/compiler manifests, bounded authenticated transfer, fair job dispatch, leases/heartbeats, cancellation, disconnect retry and stale-result refusal. Only ready opted-in participants receive jobs. Turning contribution off stops new claims and safely releases/cancels assigned work. A job result must match the requested project/revision/resources/engine before publication; preserve the last valid PDF/source on failure. Distribute independent compile jobs; do not promise that a single TeX process is split across computers. Make any compiler/package mismatch visible rather than silently changing engines.

Implementation paths: existing LAN transport/owner authorization, extension worker UI/native bridge, `runtime/chrome-extension/native/src/{main.rs,tex.rs}`, `runtime/participant-compile/{bootstrap.js,client.mjs,host.mjs}`, existing browser and artifact tests. Pass: host without TeX plus two participant contexts (one contributor, one noncontributor) collaborate; only opted-in workers claim shared contributor jobs; inherited local compilation remains available to each user; a second opt-in participant joins distribution fairly; opt-out/loss/cancel/retry cannot duplicate jobs or publish stale results; no contributors report shared compilation unavailable while stage1 local compilation remains usable; missing packages preserve source/prior output. Measure request→visible PDF, queue wait, bytes, memory and repeated use on the same fixtures/machine. Record real two-device acceptance separately. On failure keep stage 1 usable and shared compilation unavailable; preserve originals/previous PDF and repair the integration. Rollback disables contribution/dispatch, not editing or saved projects.

### Optional local research tools — stage 3 scope

**User addition, 19 November 2026:** add Python, R and installed Jupyter kernels as optional local integrations alongside optional TeX. Prioritize **mathematical error detection** and **executable academic documents**. Users select their existing environments and enable only the features they want. Offline editing/LAN and TeX contribution must still work when Python, R, Jupyter or any analysis package is absent or disabled. No subscription, paid API, cloud computation, bundled language distribution or mandatory installation. A feature may require its corresponding user-installed runtime/kernel/packages; show what is unavailable without installing anything automatically. Optional research execution also works on standalone local projects, without a host or LAN.

**Mathematical diagnostics, not formal verification.** Check only explicitly supported expressions/transformations with visible variable declarations, scope and assumptions (real/complex, sign, nonzero denominators, dimensions where supported). Report the source range, parsed interpretation, assumptions, diagnostic and reason/counterexample. Separate **issue found**, **no issue found in the supported check**, **inconclusive** and **unsupported syntax**; never show a global “mathematically correct” badge. Numerical sampling can reveal a counterexample, but cannot certify an identity. Include cancellation/domain exclusions, square roots, branch-sensitive functions, bound variables and ambiguous notation in checks. Undefined-symbol/notation findings are suggestions until project declarations/context establish an error; do not treat every unfamiliar macro or index as a mistake. Contradiction detection is limited to supported explicit constraints, not unrestricted academic reasoning. Never rewrite source automatically.

**Executable documents and generated outputs.** Reuse native source editing/completion and place execution/results controls in that UI; do not add a second notebook editor. Keep explicit cell/script identity, language/kernel, ordered dependencies and the source/data/environment revision used for each result. Store code and user-approved outputs in the project with exact export/reopen behavior and relative LaTeX references. A local computation may generate an insertable scalar, a table fragment or a figure; stage/validate outputs and ask for an explicit insert/replace action rather than rewriting the manuscript or overwriting arbitrary paths. Bind outputs to exact code/data/model inputs; mark them stale when inputs change. PDF compilation is an inherited stage1 local action, with optional shared contributor compilation added in stage3; a runtime result must not imply that an updated PDF has compiled.

**Dynamic analysis.** Initial execution is manual. Users may explicitly enable recomputation for a trusted project; invalidate downstream outputs on code/data/model changes, debounce/coalesce work, detect dependency cycles and never execute an entire project silently on open/import/join. Use the existing job identity/cancel/stale-result principles for research tasks, with a local execution adapter; do not enroll Python/R kernels in the LAN/online worker pool just because a participant contributed TeX. Local code/data stay local unless the user explicitly shares permitted inputs/results. A host or collaborator cannot select another device's environment, execute code on it or receive its datasets by granting room editing access.

**Execution and permission boundaries.** Imported/collaborator code and rich outputs are untrusted. Require explicit per-project execution consent, keep environment selection device-local, launch the intended interpreter directly (not a shell command assembled from source), and use recoverable project copies with bounded input/output, runtime/memory/process limits, cancellation and child cleanup. Do not assume TeX's sandbox safely supports general Python/R/kernel execution: inspect actual kernel subprocess/filesystem/network needs and qualify the chosen confinement before enabling it. Inherited API credentials, arbitrary home-directory access and outbound connections are not granted by selecting a runtime. Handle legitimate additional data-file permissions through explicit user selection, with no implicit broad filesystem grant. If safe confinement is unsupported, keep that execution path unavailable rather than silently run unrestricted.

Prefer the existing native bridge/private IPC to expose only the required local operations. If an installed Jupyter server is needed, use authenticated loopback-only access, validated origin/session and bounded messages; never expose its kernel ports over LAN or put its connection credentials in URLs, persistent browser storage, logs, exported projects or UI bundles. Do not forward raw startup banners that contain connection tokens. Render rich outputs as sanitized inert content with size limits; never execute notebook JavaScript/HTML or TeX shell-escape as an output-rendering shortcut. Owner permissions remain binding: a restricted participant cannot gain local persistence/export through notebooks, generated artifacts or recovery. Use session-only execution if it can uphold those limits; otherwise refuse that participant execution path visibly without granting continuation.

**Reproducibility and integrity.** Record safe project-level provenance: code/input digests, execution order, runtime/kernel/package versions, supplied random seeds and output digests, without credentials, full environment dumps or private absolute paths. Support a fresh-kernel ordered rerun and show missing dependencies/state explicitly. Preserve data/code originals and prior valid outputs on execution failure, interrupt, timeout, revoked access or interrupted publication. Numerical results can vary with environment and model assumptions; do not promise cross-machine bitwise equality or infer a valid statistical specification from a successful run. No private datasets, notebook payloads or results enter public fixtures/plans/logs.
