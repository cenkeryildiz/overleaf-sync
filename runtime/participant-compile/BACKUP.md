# Cold backup and restore

Use restic for encrypted backups of the collaboration service. Compilation stays on participants' devices. A project ZIP alone does not preserve accounts, invitations, history or recovery state.

The executable drill is `test/hosting-backup.mjs`. It creates fresh synthetic services and storage, edits and shares a multi-file project, then restores a transported encrypted repository into separate volumes. It never stops or reads the existing installation. Run from the repository with `PLAYWRIGHT_MODULE` and `CHROME_PATH` pointing to the installed Playwright module and Chrome executable. Docker must contain the exact image IDs recorded in the drill. This test is not part of the lightweight CI unit suite.

For a real installation:

1. Record immutable application, MongoDB and Redis image identities and architecture. Prepare the restic repository and a strong password stored separately from both the host and backup. Include private configuration/session keys in the encrypted snapshot; never commit them. Use a private destination with independent access controls. Retain the password offline: losing it makes the backup unrecoverable.
2. Schedule a maintenance window and stop the app cleanly, then MongoDB and Redis. Back up **all three durable volumes plus deployment configuration** while stopped. Preserve file ownership. Include the complete history/blob directories. Disposable app `tmp`, `data/cache`, `data/compiles`, `data/output` and `data/clsi-uploads` may be excluded; PDFs can be regenerated. Do not exclude unknown paths.
3. Require completed shutdown before starting the snapshot: reject OOM or forced exit137. The pinned Phusion application handles SIGTERM through all cleanup hooks then exits2; the drill accepts that only when the final post-shutdown hook marker is present. Store exits must be normal. Require successful backup exit, save its explicit snapshot ID, then run `restic check --read-data`. Only a successful verified snapshot is eligible for restore. Restart the original services after the snapshot is complete. A failed/interrupted backup never promotes a new restore point. Do not use an unqualified `latest` selector.
4. Copy the encrypted repository to independent storage. The drill simulates transport locally; **it does not establish an off-host backup**. Do not store the only password next to the repository. Set retention only after several successful restore drills; this implementation never prunes existing backups.
5. Restore the recorded snapshot with `restic restore SNAPSHOT --target FRESH_DIRECTORY --verify`, then copy into fresh named volumes with ownership intact. Never restore over the running data. Cold MongoDB files require the same pinned version and architecture; a platform migration requires a separately qualified logical backup path. Preserve replica-set member DNS aliases and private configuration. Change the site URL and external routing deliberately when moving hosts.
6. Start restored stores and app on an isolated network. Log in individually as owner and invited member, reopen the same project, export exact text/binary files, verify outsider refusal, recovery state and participant-only compilation policy. Enable public routing only after these checks and the host's authentication/TLS/security checks pass. Keep the original volumes intact until accepted.

No production backup scheduling, external storage account, public deployment or cross-architecture restore is activated by this drill.
