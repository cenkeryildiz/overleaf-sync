# Same-Wi-Fi testing on macOS

The native application remains on `127.0.0.1:8080`. The Mac's built-in Apache 2.4.67 forwards HTTP and WebSocket upgrades from one explicit private LAN address to that existing service. This adds no package, account or authentication system. The configuration has no access log, binds no wildcard/public address, and leaves native sessions, project authorization and CSRF checks in place. A changing Wi-Fi address requires regenerating the runtime configuration. This is temporary LAN testing, not internet hosting or a real-email invitation service.

Populate `httpd.conf.template` into a private runtime directory, replacing RUNTIME with that directory's absolute path, LAN_IP with this Mac's current verified private interface address, and UID/GID with its owning user. Validate with `/usr/sbin/httpd -t -f /absolute/runtime/httpd.conf`; start with `/usr/sbin/httpd -f /absolute/runtime/httpd.conf -k start`; stop with the same command and `-k stop`. No system Apache configuration, router setting or firewall rule changes. The authoritative plan records the active path, address and PID inspection command.

Online browser recovery uses `crypto.getRandomValues` to create proper independent version-4 UUIDs when HTTP LAN origins lack `crypto.randomUUID`. Its existing helper and guarded editor integration preserve writer separation. Offline service-worker preparation still requires a secure browser context and is not qualified on plain LAN HTTP. Test the actual LAN URL with two independent accounts; a browser check from the Mac cannot prove another physical device's Wi-Fi/firewall connectivity.
